# Decision log

Format: `D-nnn · status · date` then context / decision / consequences. Status: **accepted**, **open** (needs the
owner), **superseded**. Claude records routine decisions here on its own; **open** ones are the only reason to
interrupt the owner (see `.claude/skills/decide`).

## D-012 · accepted · 2026-10-15 — Git runner: no default timeout; timeouts only for network/read calls
Context: killing `git` in the middle of a local write (commit, merge, rebase) leaves `.git/index.lock` behind and
kills only the direct child (hooks, `git-remote-https`, `ssh` survive on both OSes).
Decision: `RunOpts::timeout` defaults to `None`. Fetch/push/clone and read-only queries set explicit timeouts;
local writes are cancelled only by the user (dropping the future kills the child). `GIT_EDITOR`/`GIT_SEQUENCE_EDITOR`
default to `:` so git never opens an editor; callers override per call. Credentials in URLs are redacted from
`GitError.args`/`stderr` before logging or reaching the UI.
Amendment (3.3): in `run_streaming` the timeout is an inactivity limit, reset on every stdout/stderr chunk; `run` keeps total time.
Consequences: a hung hook blocks the operation until the user cancels. Process-tree kill (Job Object / process
group) and `index.lock` cleanup are deferred to Phase 2 (2.9 undo/recovery); logged as a known limitation.
Resolved 2026-10-16 by 3.3: network ops run in their own process group (Unix) and are killed with `taskkill /T /F` (Windows) / `kill -TERM -- -pid` on cancel or timeout (`kill_tree`); `index.lock` cleanup remains with 2.9.

## D-018 · accepted · 2026-10-16 — Mutating commands emit `repo-changed` themselves
Decision: every Tauri command that writes to the repository emits `repo-changed { repoId, what }` right after git
succeeds (helper `commands::emit_changed`), in addition to whatever the debounced watcher reports. The UI refresh is
therefore immediate and deterministic (tests can assert it), and the watcher stays the safety net for external
changes. A double refresh within the debounce window is cheap (status + refs + first log page).

## D-019 · accepted · 2026-10-16 — Hunk/line staging: the backend rebuilds the patch, the UI only names the selection
Decision: the UI sends `{ target, hunkIndex, hunkHeader, lines? }`; `git-core::ops::patch` re-runs the file diff,
checks that the hunk header still matches (else `stage.stale`), builds a minimal unified patch in Rust (unselected
`+` lines dropped, unselected `-` lines turned into context, counts recomputed) and applies it with
`git apply --cached [-R] --recount` (stage/unstage) or `git apply -R --recount` (discard in the work tree). No patch
text crosses IPC, so the patch builder is unit-tested in Rust and the UI never shapes git input. Whole-file
stage/unstage/discard use `add`/`restore --staged`/`restore` + `clean -f` for untracked files.

## D-020 · accepted · 2026-10-16 — Interactive-lite rebase through a prepared todo file
Decision: `rebase_interactive` writes the todo list (pick/reword/squash/fixup/drop + reorder) that the UI chose to a
temp file and runs `git rebase -i <onto>` with `GIT_SEQUENCE_EDITOR="cp '<todo as forward-slash path>'"` (git appends
the todo path; `cp` exists in git's own `sh` on Windows and in coreutils on Linux). Paths containing `'` are rejected
with `arg.invalid`. `reword` is not offered (it needs `GIT_EDITOR`); users amend after the rebase instead. Conflicts
surface as `GitErrorKind::Conflict` and the normal abort/continue flow takes over.

## D-021 · accepted · 2026-10-16 — Undo = reflog step back with `reset --keep`
Decision: "Undo last operation" reads `git reflog show HEAD -n 2` (NUL/0x1f format), shows the subject of `HEAD@{0}`
and, when confirmed, runs `git reset --keep HEAD@{1}` on a branch (`--soft` when the entry is a plain `commit:` /
`commit (amend):`, so the undone commit's changes stay staged), or `git switch <from>` when the last entry is a
`checkout: moving from A to B`. `--keep` refuses to clobber local changes, so undo is never destructive. The reset target is the current branch's own
reflog entry {1}, taken only when the branch's latest entry is the same movement as `HEAD@{0}` (same oid and subject,
or both `rebase (finish)`), so `git stash` (which only writes `reset: moving to HEAD` on HEAD) leaves nothing to undo. Detached HEAD
or a reflog with one entry disables the action. Branch deletion is undone separately by the delete dialog, which
reports the deleted tip oid for `branch -c`.

## D-022 · accepted · 2026-10-16 — In-progress operation state read from the git dir, external editor via config
Decision: `ops::state::in_progress(info)` inspects `git_dir` for `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`,
`rebase-merge/`, `rebase-apply/` (no git spawn) and reports `{ kind, headName?, onto?, done, total }`; the UI polls it
with `repo_status` on `head`/`index` changes and shows a conflict banner with abort/continue. "Open in external

falls back to revealing the file in the file manager (never the OS default handler, which could run a tracked script)
until settings (6.3) add an editor path.

## D-024 · accepted · 2026-10-16 — Askpass bridge: one keyring entry per host, the app binary answers git itself
Context: item 3.2 needs `git` over HTTPS to use the token the app stores (5.1) without the user's own credential

## D-025 · accepted · 2026-10-19 — Worktree listing uses `git worktree list --porcelain` without `-z`
Context: `-z` for `worktree list` needs git 2.36; `MIN_GIT_VERSION` is 2.31 and Ubuntu 22.04 ships 2.34.
Decision: parse the line-oriented `--porcelain` output (records separated by a blank line). Lock/prune reasons
with unusual characters arrive C-quoted (core.quotePath style) and are unquoted by the parser; paths are not quoted
by git in this mode, so a path containing a newline is the one unsupported case. Unknown attribute keywords are
ignored so newer git versions do not break the list.
Consequences: a pure parser with unit tests on captured samples; revisit `-z` when the floor rises to 2.36.

## D-028 · accepted · 2026-10-19 — Pull requests: repo slug from the remote URL, checkout like `gh pr checkout`
Context: items 5.4–5.6 need to know which GitHub repository a local repo maps to, and how "checkout PR" behaves for
same-repo and fork PRs.
Decision: (1) The slug (owner/name) is parsed in `github-api` from the remote URL (https, ssh and scp-like forms of
github.com); `origin` wins, else the first github.com remote; no match means the PR features stay hidden. (2)
Checkout of a same-repository PR fetches the remote and checks out a local branch named after the head ref, tracking
`<remote>/<head>` (an existing local branch of that name is reused, not reset). A fork PR fetches
`+refs/pull/N/head:refs/remotes/<remote>/pr/N` and checks out a local branch `pr/N` at it without upstream. The
sequence is one git-core op (`ops::pull_request::checkout_pr`) tested on a fixture pair of repositories. (3) PR
lists are read-only summaries (open/closed/all from the API; "mine" filtered in the UI by the signed-in login);
detail fetches the PR, its reviews, and the head commit's check runs + combined status, in that order. (4) PR body
is shown as plain text in Phase 5; markdown rendering is a Phase 6 polish item.
Consequences: `FetchArgs` gains `refspecs`; `github_repo_slug`, `github_pulls`, `github_pull`, `github_checkout_pull`
Tauri commands; the checks summary type is shared with the graph decorations of 5.6.

Amendment 2026-10-19: the fork PR head is fetched to `refs/pull/<remote>/N` (not `refs/remotes/<remote>/pr/N`), so
`fetch --prune` cannot delete it and a real remote branch `pr/N` cannot collide; local `pr/N` is created from it.
Checkout never relies on `branch.autoSetupMerge`: same-repo uses `switch --track`, forks `switch --no-track`.

## D-031 · accepted · 2026-10-22 — Filtered log pages share the graph cache; parents pruned per batch
Context: "load more" on a filtered graph re-ran `git log` from commit 0 with a growing limit and re-laid out the
whole prefix every page (item 7.5).
Decision: the filtered log goes through the same per-repo single-slot cache as the unfiltered one, keyed by
`(order, all, author, message, path)`; page 1 is fetched with the requested limit, the next request fetches the
whole remainder in one call and later chunks come from memory. Parents absent from a filtered batch are pruned per
batch, so a filter matching more than one page shows one lane break at the page boundary. The exact alternative
(fetch the whole filtered set before painting page 1) costs a full history walk on path filters and was rejected.
Consequences: `graph.out_of_order` when `skip > 0` arrives with a different filter (the UI never sends it: a filter
change reloads from 0). A filter change waits for an in-flight remainder fetch on the per-repo lock.

## D-033 · accepted · 2026-10-22 — Redo re-applies the HEAD recorded before the undo; terminal is an argv launcher
Context: item 8.3 adds Redo next to the reflog-based Undo (D-021) and a Terminal button (D-030 (8)).
Decision: `undo_last` records HEAD (branch via `symbolic-ref`, oid via `rev-parse`) before undoing and returns
`UndoOutcome { info, redo: UndoAction, head, branch }`. The redo action mirrors the undo kind (`reset --soft` /
`--keep` back to the recorded oid, `switch` back to the recorded branch or detached oid). The UI keeps one redo per
repository and drops it as soon as HEAD's oid **or** branch differs from `head`/`branch` (two branches can point at
the same commit). `apply_action` is the shared executor and validates targets (full oid for resets and detached
checkouts, plain branch name otherwise) because the redo comes back from the UI over IPC. There is no redo stack.
Terminal: `terminal_candidates` yields argv lists (settings override split by `split_words`, then `wt.exe -d .` /
`cmd.exe` on Windows, `$TERMINAL` / `x-terminal-emulator` / `gnome-terminal --working-directory` /
`konsole --workdir` / `xterm` on Linux); the first program found on `PATH` is spawned with cwd = work tree, a new
console on Windows (stdio inherited so `cmd.exe` stays open), detached stdio on Linux, and reaped in a thread.
Consequences: a redo after an undo of a checkout returns to the branch, not to the exact oid, when the branch has
since moved; the user override is never passed through a shell.

## D-034 · accepted · 2026-10-22 — Commit identity via `git config --show-scope`; avatars fetched by the backend
Context: item 8.4 shows the effective commit signature and the signed-in user's GitHub photo (D-030 (4)).
Decision: `identity()` reads `user.name` / `user.email` with `git config --show-scope --get` and reports the scope
git prints (`local`, `global`, `system`, `worktree`, `command`); `set_identity(scope: Local | Global, ..)` writes
both keys after validation (trimmed, non-empty, no newline/NUL). The avatar is downloaded by `github-api`
(`avatars.githubusercontent.com` / `github.com` only, `s=64`, 2 MiB cap, `image/*` only, no `Authorization`
header: the token never goes to the CDN) and cached by the app as `<cache_dir>/avatars/<login>.<ext>` for seven
days; the command returns a `data:` URL or `None` on any failure, never an error toast. Logins are validated
(`[A-Za-z0-9-]`) before they touch a path.
Consequences: the webview never fetches from GitHub itself; offline, a cached avatar still shows.

## D-035 · accepted · 2026-10-23 — Author photos only for known GitHub authors; co-author trailers leave the body
Context: Phase 9 wants GitKraken-style avatars in the details pane, but D-023 keeps avatars offline because
resolving an arbitrary author email through a third party leaks the email.
Decision: (1) The frontend maps an author email to a GitHub login only when it needs no lookup:
`<id>+<login>@users.noreply.github.com` / `<login>@users.noreply.github.com`, or the signed-in account's own
email (`loginForAuthor`, pure). Only then is the photo requested through the existing backend command
(`github_avatar(login)`, D-034 cache + one-hour negative cache). Everyone else keeps the initials badge, and the
graph nodes stay initials for all authors (no per-row network). Gravatar stays out. (2) `commit_details` asks
git for `%(trailers:key=Co-authored-by,valueonly,unfold)` and strips those lines from the body itself, following
git's trailer rules (last paragraph only, no indented keys, optional space before `:`, folded continuations,
CRLF preserved) and never more lines than git parsed, so prose that merely mentions `Co-authored-by:` survives.
Consequences: no author email ever leaves the machine; `coAuthors` is a separate field on `CommitDetails`;
git >= 2.22 is needed for `%(trailers:...)`, already implied by `MIN_GIT_VERSION` 2.31.

## D-036 · accepted · 2026-10-23 — Known-author photos also in the graph; the git identity counts as "me"
Context: after the Phase 9 review the owner wants the GitHub photo on graph nodes too, and their commits carry the

## D-038 · accepted · 2026-10-25 — Author photos by email for GitHub-hosted repos
Context: with D-035/D-036 only the signed-in user and noreply authors got a photo; the owner saw initials for
their own commits in one repo (the mapping depended on the repo's git identity and the account email) and asked
why other authors with a GitHub account, and `noreply@anthropic.com` co-authors, stay initials.
Decision: amends D-035 (1) and D-036. For a repository that has at least one GitHub remote, an author email that
the lookup-free path cannot map is sent to GitHub's avatar CDN (`/u/e?email=`), which answers with the photo of
the account owning the address or with one fixed default image. The backend (`github_avatar_email`) fetches the
default once per process for a sentinel `.invalid` address and reports `null` when the bytes match, so unknown
authors keep the initials badge. No token, no API quota, disk cache keyed by an (unsalted) SHA-256 of the
address, the address is never logged. At most four downloads run at once; a "no photo" answer drops any stale
cached photo and is remembered for an hour, the frontend retries a `null` after ten minutes. Repos without a GitHub remote keep D-035: no email leaves the machine.
Consequences: the privacy argument of D-023 narrows to "no new information": the authors of a GitHub-hosted repo
are already on GitHub with those addresses. The lookup-free path stays first, so the signed-in user's photo still
shows offline and in non-GitHub repos. One CDN request per distinct unknown author per hour at most (negative
cache), plus one for the sentinel per launch; a changed default image on GitHub's side is harmless (a mismatch
only shows the default picture until the sentinel refreshes on the next launch).

## D-037 · accepted · 2026-10-24 — Tab aliases in the session; quiet fetch on show; remote checkout pulls
Context: owner feedback after Phase 9: a dozen tabs overflowed into a scrollbar, tab names are folder names
(not always meaningful), remote refs were stale until a manual Fetch, and double-clicking `origin/x` when `x`
already existed locally only switched branches.
Decision: (1) Tab aliases are per repository path and live in `session.json` (`aliases`, serde default), kept
for closed repos so an alias survives close/reopen; the folder name stays the fallback and the path stays the
tooltip. Tab order is the order of the `open` array (drag to reorder), still grouped worktree-with-main by
`orderTabs`. (2) Showing a repo (open, restore, tab switch) runs a quiet `git fetch --all --prune`: progress bar
and cancel as usual, no toasts (errors only to the console), skipped when busy, when the repo has no remotes or
when the last quiet fetch for that repo finished under 60 s ago. (3) `checkout(<remote>/<branch>)` with an
existing local `<branch>` switches to it and then pulls `<remote> <branch>` (pull strategy from settings), so
"checkout a remote branch" always leaves local == remote; without a local branch git-core keeps creating the
tracking branch. (4) When nothing is selected after a graph load, the first visible row is selected (WIP when
shown, else the first commit) unless a pull request is being viewed.
Consequences: the session file gains one map; a repo with a stale remote may show a short progress bar on every
tab switch after a minute; the pull after a double-click only runs when the local branch is not ahead of its
upstream (a diverged branch gets a toast instead, never an unasked merge or rebase). The window sets
`dragDropEnabled: false` (tauri.conf.json): Tauri's native drag-drop handler otherwise swallows HTML5 drag events
in WebView2, which the tab reorder and the branch chip drag rely on; the app has no file-drop feature.
